# Алгоритм вывода context_id и план TTL (черновик)

> Неделя 1, пуш 5 (Р5). Согласуется с Р1 (место вызова в конвейере) и Р2
  (нормализованные ключи — docs/ml/marker-scheme.md §2).

## Постановка

MVP работает без серверного состояния: история диалога передаётся клиентом явно
в `input` (ТЗ п.6). Значит, при каждом запросе сервис должен сам определить,
к какому контексту относится диалог, чтобы:

- нумерация маркеров продолжалась (PERSON_1 в новом сообщении = тот же человек);
- обратная подстановка знала исходные значения прошлых маркеров.

## Алгоритм (выбранный): context_id по нормализованным значениям

Клиент присылает историю: пользовательские тексты — исходные (с ПДн), ответы
модели — с маркерами. Сервис обрабатывает пользовательские тексты конвейером Р2
и получает набор нормализованных значений. Дальше:

```
resolve_context(user_id, normalized_values) -> context_id:
    candidates = store.find_contexts_by_values(user_id, normalized_values)
    # {context_id: число совпавших значений}

    если candidates пуст:
        context_id = uuid4()          # новый диалог
    иначе:
        context_id = argmax по числу совпадений
        при равенстве — контекст с последним created_at
    вернуть context_id
```

Новые значения из текущего запроса дописываются в выбранный контекст (метод
`put`); значения, которых там ещё не было, получают следующие свободные номера
через `get_by_value` + подсчёт занятых маркеров типа.

Реализация `find_contexts_by_values` уже в `SqliteMappingStore`; сам
`resolve_context` подключается в конвейере `/v1/responses` в неделе 2–3 (Р1+Р5).

## Пограничные случаи

| Случай | Поведение | Обоснование |
|---|---|---|
| Два пользователя с одинаковым текстом | разные контексты | изоляция по user_id (ТЗ п.3, п.9) |
| Один пользователь, два диалога об одном человеке | контексты сольются | компромисс MVP: значения те же → маркеры и восстановление корректны |
| Значения из разных старых контекстов в одном запросе | побеждает контекст большинства | диалог «разветвился»; меньшинство получает новые маркеры |
| Маркер из ответа модели, которого нет в таблице | не восстанавливается | требование ТЗ: неизвестные маркеры передаются как есть |
| Истёк TTL у записей контекста | контекст не находится | просроченное = отсутствующее; создаётся новый контекст |

## План TTL-очистки

- `put` пишет `expires_at = now + ANONGW_MAPPING_TTL_HOURS` (по умолчанию 24 ч).
- Любое чтение (`get`, `get_by_value`, `find_contexts_by_values`) фильтрует по
  `expires_at > now` — просроченные записи не видны до физического удаления.
- Фоновая задача (неделя 2; ревизия — неделя 4): задача lifespan приложения,
  каждые 60 секунд вызывает `cleanup_expired()` и логирует число удалённых
  записей. Ошибка одной итерации (сбой базы) не убивает задачу — логируется и
  цикл продолжается. Интервал и TTL — настройки окружения, строго положительные.
- Аварийная остановка задачи не влияет на корректность: фильтрация по
  `expires_at` идёт в каждом запросе.

## Схема хранения

`src/anongw/mapping/schema.sql`: уникальность `(user_id, context_id, marker)` и
`(user_id, context_id, normalized_value)` (NULL не конфликтует), индексы по
`expires_at` и `(user_id, normalized_value)` под поиск контекстов.
