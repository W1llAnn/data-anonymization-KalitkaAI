# Git-workflow: ветки, пуши и мержи

> Полная последовательность разработки: неделя = интеграционная ветка, внутри недели — роль-ветки с фиксированной очерёдностью пушей.
> Правила зафиксированы командой и не меняются по ходу без решения всей команды.

## 1. Общая схема ветвления

- **`main`** — защищённая ветка. Прямые пуши в `main` запрещены; изменения попадают только через merge недельной ветки.
- **`week-NN`** (`week-01` … `week-11`) — интеграционная ветка недели. Создаётся от `main` в начале недели (ответственный — Р1). Нумерация соответствует неделям плана спринтов.
- **`week-NN-rX-тема`** — роль-ветка. Создаётся от `week-NN` (после мерджа предыдущей роль-ветки, если есть зависимость). Владелец — соответствующая роль. Дефис вместо слэша: git не позволяет одновременно существование веток `week-NN` и `week-NN/...`.

Недельный цикл:

```
main ──┬──────────────────────────────── merge week-01 ────────┬── ...
       └── week-01 ──┬─ merge r1 ─┬─ merge r2 ─┬─ ... ─┬─ merge r6 ─┘
                     │            │            │       │
                     ├─ week-01-r1-...   (пуш 1, первым — каркас/контракты)
                     ├─ week-01-r2-...   (пуш 2, параллельно)
                     ├─ week-01-r3-...   (пуш 3, параллельно)
                     ├─ week-01-r4-...   (пуш 4, параллельно)
                     ├─ week-01-r5-...   (пуш 5, параллельно)
                     └─ week-01-r6-...   (пуш 6, последним — тесты поверх всего)
```

## 2. Правила

1. **Мерж — только через ветки.** Прямых коммитов в `main` нет; `week-NN` получает изменения только через merge роль-веток.
2. **Один PR = одна роль-ветка** = задачи одной роли на неделю. Название PR: `[Неделя N][РX] тема`.
3. PR мержится в `week-NN` только при зелёном CI и ревью (Р1 или назначенный ревьюер).
4. **Порядок мержей = порядок пушей** (таблица §4). Роль-ветка создаётся от `week-NN` с уже вмерженным предыдущим зависимым этапом.
5. **Ветки не удаляются** — ни роль-ветки, ни недельные, ни после мерджа в `main`. История веток сохраняется для аудита и разбора полётов.
6. Мерж `week-NN` → `main` выполняет **Р1** в конце недели, только после выполнения DoD недели.
7. Force-push в общие ветки (`main`, `week-NN`) запрещён. В свою роль-ветку — допустим до открытия PR.
8. Если DoD недели не выполнен — мерж в `main` переносится, это отмечается в файле недели `docs/weeks/week-NN.md`.

## 3. Единый порядок пушей в течение недели

| Пуш | Кто | Что | Почему такой порядок |
|-----|-----|-----|----------------------|
| 1 | Р1 | каркас/контракты недели (схемы, интерфейсы, инфраструктура) | остальные ветвятся от результатов |
| 2–5 | Р2, Р3, Р4, Р5 | задачи ролей недели | параллельно; порядок между собой свободный, если в таблице §4 не указана зависимость |
| 6 | Р6 | тесты и проверки поверх собранного | тестам нужен результат остальных |

Исключение — неделя 9: первым пушит Р6 (замеры и SDK-прогон запускают цикл багфиксов), далее роли пушат фиксы.

## 5. Протокол конца недели (merge в main)

1. Р6 прогоняет полный CI и интеграционные тесты на `week-NN`.
2. Р1 сверяет DoD недели (файл `docs/weeks/week-NN.md`).
3. DoD выполнен → Р1 открывает PR `week-NN` → `main` («Неделя N: итоги»), ревью — любой второй участник, мерж.
4. DoD не выполнен → перенос, пометка в файле недели, `week-NN+1` создаётся от `week-NN` (а не от `main`) до закрытия долгов.
5. **Ветка `week-NN` и все роль-ветки остаются в репозитории** — удаление веток запрещено.
